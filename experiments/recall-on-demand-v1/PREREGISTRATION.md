# Recall on demand v1: pre-registration

**Written 2026-10-30, before any model call. Self-reviewed.** Run by a Claude Code cloud session at the owner's request ("proceed with whatever you can do").

## Why

Compression has reached its safe ceiling on real agent traffic:
- discourse compaction gives about −52% tokens;
- guarded pruning adds 1.5%, and tool-output transforms an estimated 5.7% ([guarded-codec-v1](../guarded-codec-v1/STAGE1-RESULTS.md), [tooloutput-codec-v1](../tooloutput-codec-v1/PREREGISTRATION.md)).

The same stage-1 run showed a bigger problem. In **30 of 44** questions, the fact the model needed was **no longer in the prompt** at all, because older history had been cut under context pressure.

This experiment asks whether a small context plus an **exact recall tool** over the full stored history brings those facts back. That would make the memory lossless for the system while keeping the prompt small (ADR 0026, checkable memory).

## Data

- The transcript of the Claude Code session running this experiment, frozen at commit time by copying it to a private file. It is real agent work: tool calls, tool results, reports, English and Greek.
- It stays private. Only aggregates are published, plus the SHA-256 prefix of the frozen copy (recorded in `results.json`).
- Messages are built as in [session-transcript-compaction-v1](../session-transcript-compaction-v1/measure.mjs): owner text, assistant text, tool calls and tool results, without thinking blocks.

## Points and views

**Points:** 10 owner-text turn boundaries, evenly spaced over those with at least 300 earlier messages. The selection is deterministic, in [`run.mjs`](run.mjs).

At each point, everything before the boundary is the history:
- **Budget view.** `planDiscourseCompaction(history)` with default options, then the **most recent compacted messages up to 30,000 characters**. Older messages are absent. This stylises context pressure.
- **Full store.** Every discourse unit of every history message, verbatim. This is what the recall tool searches.

## Items

For each point, candidate facts come from history messages **outside** the budget view:
- a literal spelling of 4 or more characters (core `literalSpellings`: paths, hashes, identifiers, multi-digit numbers);
- the literal must not appear anywhere in the budget view text;
- it must occur in at most 3 history messages (a distinctive fact);
- excluded: literals that are bare numbers of 4 digits or fewer (years, counts that are easy to guess) and literals inside the frozen transcript path.

The items are seeded-ordered (SHA-256 of `rod-v1:` + literal), at most 4 per point, one per literal. **A literal is used at one point only**, in point order, so items do not repeat across points.

**Questions:**
- **Generation:** Haiku writes, once per point, one question per item. It sees only the source unit (at most 600 characters) and the literal, and must not include the literal.
- **Rejection:** questions containing the literal are rejected and counted.
- **Freezing:** questions are frozen before any answer call.

## Conditions

Every condition has the same instructions, questions, grader and model (`claude -p --model haiku`, one call per point per condition):

| Condition | What the model has |
|---|---|
| **A: budget** | The budget view only, no tools |
| **B: budget + recall** | The budget view, plus one MCP tool, `recall(query)`. It does a deterministic search over the full store and returns the top 5 units, each up to 800 characters, with message index and role. The model is told it may use it when the context does not state the answer. |
| **C: oracle (reported only)** | The budget view plus each item's source unit appended. An upper bound for answerability. |

**Grading** uses stage 1's literal-containment rule: numbers must match exactly, and any other literal is matched as a case-insensitive substring. An answer of "unknown" is wrong.

## Bars

| # | Bar |
|---|---|
| 1 | Accuracy B ≥ accuracy A + 30 percentage points |
| 2 | Accuracy B ≥ 60% |
| 3 (reported, not a bar) | Input tokens per call (usage, including cache) for A, B and C; recall calls per question |

Expected result, recorded before running: **A near 0%**, because the literal is absent from its view by construction. Bar 1 therefore mostly tests B. The interesting numbers are B's accuracy against C's, and B's token cost against A's.

## Budget and stopping

- **Cap: $8** for Haiku, covering questions and all answers.
- The run stops before the cap is passed. Incomplete results are reported as incomplete.
- No tuning after any answer is seen.

## Limits

- **One session, which is unusual:** very long, and about Lunum itself.
- **Synthetic questions:** generated by a model.
- **One answering model:** Haiku.
- **Search method:** the recall tool is a simple deterministic term search, not the production locator.
- **The budget view is a stylised stand-in** for OpenUnum's live cut, not the live prompt itself.
